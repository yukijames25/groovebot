# GrooveBot — 歌声・ハミングにリアルタイムで“ノる”上半身ロボット

> アカペラの歌声やハミングを聴いて、テンポと盛り上がり・曲調に合わせて上半身でグルーヴするロボットの研究開発プロジェクト。

GitHub: https://github.com/yukijames25/groovebot

---

## 一言で

「人が鼻歌を歌うと、ロボットがその場でノリ始める」という体験を、**伴奏なし・リアルタイム**で成立させることを目指した個人R&Dプロジェクト。音楽情報処理（MIR）・ロボット制御・人とロボットの引き込み（entrainment）の交差点に位置する。

## なぜ難しく、なぜ面白いか

- **入力がアカペラ／ハミング**。伴奏のある楽曲と違い、和声も打楽器もない単旋律から「いつ・どれくらい・どうノるか」を取り出す必要がある。
- **リアルタイム性**。聴いてから動くまでの遅延が体験を殺す。知覚と制御を分離し、低遅延で回す設計が要る。
- **身体非依存**。自作3Dプリントロボット／Pepper／シミュレータなど、どの“体”にも載せ替えられること。

研究的には、音楽駆動のロボットダンス、リズム的引き込み、オンラインビート追跡、音楽感情推定、music→dance生成といった複数領域の知見を踏まえて設計している。

## 問題の二分割

最初に問題を二つの独立した軸に分けたことが、以降すべての設計判断の土台になっている。

- **いつ動くか（timing）** = 拍・テンポ・構造。→ 参照アライメント系。
- **どう動くか（style）** = 曲調から動きの質（どのグルーヴ・どれくらいの強度）を決める。→ 学習ベースの GrooveStyleSelector。

この二軸は別々に開発・検証でき、片方の進捗がもう片方を待たない。本ドキュメントもこの二軸で構成する。

## システム設計

「いつ動くか」と「どう動くか」を分け、**頭脳と身体を完全に分離**したインターフェース駆動の構成を採った。

```
歌声/ハミング ──┐
               ▼
   ┌─────────────────────────────────────────────┐
   │ STYLE（どう動くか）                          │
   │  audio → mel → 凍結PANNs CNN14 → マルチヘッド │
   │    ├ genre   (分類)                          │
   │    ├ arousal (回帰, DEAM学習)                │
   │    ├ valence (回帰, DEAM学習)                │
   │    └ mood    (V/A circumplex由来)            │
   │         ▼                                    │
   │   属性テーブル(genre×arousalバケット×mood)   │
   │         ▼  style + intensity                 │
   └─────────────────────────────────────────────┘
               │
   ┌───────────┴─────────────────────────────────┐
   │ TIMING（いつ動くか）                         │
   │  ReferenceAligner: 選曲した既知曲の参照へ生歌声を整合 │
   │  → 拍位相 / テンポ / 構造 を継承             │
   └───────────┬─────────────────────────────────┘
               ▼
   グルーヴ生成器（StyleGrooveGenerator + 拍位相つきプリミティブ）
               ▼
   JointCommand（関節指令, URDF関節上限でクランプ）
               ▼
   RobotBackend（MuJoCo sim / Pepper / 自作機 を差し替え可能）
               ▼
   ロボットの動き  ──→  ナレーター（perception→decision→action を言語化, 観測専用）
```

- **Orchestrator** が制御ループ（30–50Hz）を回し、重い知覚処理から分離。
- 公開インターフェース（`GrooveContext` / `JointCommand` / `RobotBackend`）を固定契約として保ち、頭脳が特定のシミュレータやロボットSDKに依存しないようにしている。**全期間を通じてこの3つのIFは不変**。
- 関節出力は常にURDFの関節上限へクランプ（安全要件）。

## 技術的な意思決定のハイライト

このプロジェクトで最も価値があるのは、コードそのものより**証拠に基づいて方針を変えた判断**だと考えている。

### 1. 盲目ビート追跡から「参照アライメント」への転換（timing）

当初はライブ音声から直接ビートを推定する方針（BeatNet/madmom）で進めたが、**madmom が現代環境（Python 3.12 / numpy 2.x）で構造的に動かない**ことが判明。小手先の回避を続けず、**ターゲット用途（カラオケ＝既知曲）の性質を使って問題を作り替えた**：ユーザは曲を選ぶ → その曲の参照（拍・構造・特徴量）を持てる → ライブ歌声を参照タイムラインへ整合させる → 不安定な盲目追跡なしに**信頼できる拍グリッドと構造を継承**できる。盲目追跡は任意フォールバックへ降格した。

### 2. 「NNは確率計算機」— 学習させる所と、させない所の線引き（style）

「どう動くか」は、**学習で解く部分と、ルールで書く部分を明確に分けた**のが肝。

- **学習するのは audio → 属性（genre / arousal / valence）だけ**。ここは音から感じ取る知覚問題。
- **属性 → グルーヴの対応は人手のテーブル**（genre × arousalバケット × mood → style + intensity）。これは「設計判断」であって学習対象ではない。
- 結果、教師データは**著作権の重いライブ演奏映像ではなく、CCの音楽タグ付けデータ**で済む。RLでもなく、素直な分類＋回帰。

「NNが勝手に解いてくれる」のではなく、**何を教師信号にするかが本質**、という理解に立って設計している。

### 3. 評価ファースト／誠実な実証主義（全体）

機能を足す前に評価ハーネスを用意し、**良い数字も悪い数字も同じ物差しで**判断する。実データのスコアが低い時は、結果を鵜呑みにも棄却もせず「タスクが本当に難しいのか／計装のアーティファクトか」を切り分ける。修正は**正解データで出力を調整しない（テストリークを避ける）**形でのみ行う。

## 主要な結果

### TIMING ブランチ

#### M1 — リアルタイム・グルーヴループ（完了, tag m1）
知覚から分離した30–50Hzの制御ループ、型付きインターフェース、ルールベースのグルーヴ生成、URDF関節上限クランプまでを実装。

#### M0′ Tier 1 — 参照アライメントの実現性検証（強い結果）
参照（ボーカル＋拍グリッド）に既知のテンポ変動を与えた合成クエリを、オフラインDTWで整合し拍復元精度を測定（GTZAN系7ジャンル×複数曲×5倍率 = 70ラン）。

| 指標 | 値 |
|---|---|
| F-measure（全体） | **0.983** |
| CMLt / AMLt | 0.984 / 0.984 |
| リアルタイム係数 | 0.017（約60倍速） |

特筆は **CMLt ≈ AMLt（半・倍テンポの取り違えがゼロ）**。盲目追跡が最も苦手とする領域であり、参照アライメント方式の**構造的な強み**がそのまま数字に出た。自己ワープゆえ楽観値であることは最初から切り分けている。

#### M0′ Tier 2 — 実演奏での頑健性（PARKED）
実アマチュア歌手の独立演奏（DAMP系）で測る経路を実装。賛美歌データ（Amazing Grace, 17,582独立演奏）での検証を通じ**評価パイプラインを方法論的に堅牢化**したが、Amazing Grace は遅いルバート賛美歌＝**病的な外れ値**（人間でも拍が取りにくく、そもそもグルーヴ対象でない）と判断し最適化を打ち切り。代表値判定は**テンポ安定なポップ（DAMP-VSEP）**で取る方針で、現在**アクセス許諾待ちのため健全にPARKED**。Tier 1 で機構は検証済み。

### STYLE ブランチ — GrooveStyleSelector

#### genre 分類 — 転移学習で実用域へ
from-scratch CNN（GTZAN fault-split）では test 0.43、過学習ギャップ +0.22、pop-sink。**凍結 PANNs CNN14 → MLPヘッド**に切り替え、**fault test 0.43 → 0.82（+38.6pt）**、過学習ギャップ +0.03、pop-sink解消。用途に対し十分と判断しクローズ。（PANNsのAudioSet事前学習が分布的に重なる点は正直な但し書きとして明記。）

#### arousal / valence 回帰 — DEAM で学習・検証
DEAM（1,802曲, V/A連続ラベル, CC BY-NC）で**凍結PANNs → 回帰ヘッド**を学習。

| 指標 | 学習ヘッド | 既存ヒューリスティック |
|---|---|---|
| arousal | **R²=0.522 / r=0.723**（文献≈0.6） | r=0.422（+0.16の過大評価バイアス） |
| valence | **R²=0.451 / r=0.675**（文献≈0.4を上回る） | — |

→ ヒューリスティックを置換し、**学習ヘッドを既定**に（PANNs無し環境のみヒューリスティックにフォールバック）。

#### mood — V/A circumplex 由来
DEAMの V/A から circumplex の4象限（happy / aggressive / calm / sad）を**クリーンに導出**。epic / dark は純V/Aで表せないため既定オフ。MTG-Jamendo の mood ヘッド（test 0.35, calm-sink）より V/A 由来の方が安定と判断。

#### JointCommand ブリッジ ＋ 拍位相規約
`StyleGrooveGenerator` と8種の上半身ムーブ・プリミティブ（headbang / bob_nod / sway / front-back rock / fist_pump / clap / penlight_wave / quiet_listen）を JointCommand 経由で MuJoCo に接続。**ナレーター**（perception→decision→action を言語化, 制御パス外の観測専用）を入れた所、**headbang が拍からずれて頂点を迎えるバグを即座に発見**。修正後、拍位相の契約を確定：

| 種別 | ムーブ | 周期 | 頂点 |
|---|---|---|---|
| accent | headbang / bob_nod / fist_pump | 1拍 | 毎拍 (1+cos2πb)/2 |
| accent | clap | 2拍 | 2 & 4（バックビート） |
| continuous | sway / rock / penlight_wave | 2拍 | 拍でゼロ・半拍で最大 sin(πb) |
| minimal | quiet_listen | — | なし（呼吸のみ） |

#### affect バケットの分位点較正 ＋ 日本語汎化テスト（最新）
end-to-endショーケース（西洋2本＋**CC日本語2本**を全パイプラインに通しGIF＋ナレーション生成）が、**部品テストをすり抜けた潜在バグを捕捉**した：回帰ヘッドの平均回帰で arousal 出力が中央に圧縮され、絶対閾値 0.33/0.66 に対し**全クリップが mid バケットに沈み**、日本語2本が clap に収斂していた。

修正は**4本に過学習しない原理的なやり方**で行った：バケット境界を **DEAM val プール（n=270, ショーケース4本は held-out）の三分位（tertile）**から導出し（low<0.410 / mid / high≥0.529）、`affect_calibration.json` を単一の出所としてコード全体が参照する形に。再走後、**日本語2本の arousal が high / mid に正しく割れ、intensity が 0.92 vs 0.57 と明確に分離**（較正前は両方 mid・差ほぼ無し）。

この過程の副産物が本命の問いへの答えになった：**「日本語楽曲に対応するのに再学習は不要、必要だったのは較正」**を実データで確認。arousal は言語非依存に妥当な値を返し、PANNsバックボーンも多文化（AudioSet）由来で偏りは genre ヘッドのラベル側に限局する、という仮説が支持された。

## このプロジェクトが示すもの

- **誠実な実証主義**: 良い数字（Tier 1 の 0.98、転移後の genre 0.82）も悪い数字（実データ初回スコア、平均回帰）も同じ規律で扱う。低スコアは「難しさ」と「計装アーティファクト」を切り分け、修正はテストリークを避ける形でのみ。
- **判断の規律**: Amazing Grace（非代表な外れ値）への過剰最適化を意図的に打ち切る。日本語クリップで clap が出ても「妥当な着地か」で評価し、headbangに矯正しない。
- **システム思考**: 身体非依存IF、知覚と制御の分離、安全クランプ、観測専用ナレーター。**公開IFは全期間不変**。
- **証拠駆動の方針転換**: madmom行き止まり→参照アライメント。from-scratch→転移学習。ヒューリスティック→DEAM学習ヘッド。
- **学習とルールの線引き**: 学ぶべき所（audio→属性）と設計すべき所（属性→groove表）を分け、教師データの著作権問題を回避。
- **ライセンス／著作権の衛生**: ライセンスデータ（DAMP/Smule, MTG, DEAM, GTZAN）は一切公開リポジトリへコミットせず、`data/`（gitignore）にローカル限定・再配布禁止を徹底。

## 技術スタック

Python / librosa / mir_eval / pretty_midi / PyTorch / PANNs（panns_inference, 凍結CNN14）/ MuJoCo（バックエンド）/ NumPy・SciPy。仕様駆動開発（SRS+SDDの`SYSTEM_SPEC.md`）、430件超の自動テスト、AIエージェント（Claude Code）併用の開発ワークフロー。

## 現在地と今後

- **STYLE**: v1完成＋観測可能＋拍位相正確＋affect較正済み。日本語汎化は arousal/intensity 軸で実証。
- **TIMING**: Tier 1 で機構検証済み。代表値判定は DAMP-VSEP アクセス待ちで健全にPARKED。
- **残る限界（正直に）**: (1) genre ヘッドのドメイン外（J-pop/J-rock未学習）由来の move 多様化不足（pop-sink → clap収斂）。防御設計によりstyleは壊れないが多様性は損なう。(2) 回帰ヘッドの平均回帰による分散の狭さ→バケット境界付近の不安定性。
- **M2**: オンライン整合（score-following）＋ Orchestrator 接続。Tier 2 の科学的検証後に着手。
- **M3**: 構造条件付けの**学習グルーヴ生成**（VQ-VAE codebook 等, 手作りプリミティブを置換, AIST++/GPU想定）。
